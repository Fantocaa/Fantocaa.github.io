Multi-Tenant Event Platform

The platform operator serves multiple event organizers. Each organizer needs a place to manage its events and guests, while the operator needs to create and administer those separate workspaces. Mixing both responsibilities in one shared data space makes it hard to know which organization's records a request belongs to.

The problem to solve

The difficult part was the boundary between platform administration and an organizer's day-to-day work. A new organizer needed a usable workspace, not just an account. Once that workspace existed, its event data had to stay tied to the right organization on every request.

How I approached it

I separated the central tenant and access records from the event and guest records owned by each tenant. A subdomain identifies the organizer's context; its own PostgreSQL database holds its operational data. I also connected tenant creation to database setup, migrations, and initial roles and menus, so provisioning a workspace prepares the application to be used.

Laravel handles the tenant lifecycle and requests, while React and Inertia provide the interface. Redis supports sessions, caching, and queued work. Those tools serve the underlying decision: shared platform administration, separate organizer workspaces.

What this delivers

The operator can set up and manage organizations without putting their event data in the shared administrative space. Each organizer works with its own events and guests through its own subdomain.

Platform Acara Multi-Tenant

Operator platform melayani beberapa penyelenggara acara. Masing-masing penyelenggara membutuhkan tempat untuk mengelola acara dan tamunya, sementara operator perlu membuat dan mengatur ruang kerja yang terpisah. Jika dua tanggung jawab itu dicampur dalam satu ruang data, kepemilikan tiap catatan menjadi sulit dibedakan.

Masalah utamanya

Tantangannya adalah memisahkan pekerjaan operator platform dari pekerjaan harian penyelenggara. Saat organisasi baru bergabung, mereka membutuhkan ruang kerja yang siap dipakai, bukan sekadar akun. Setelah itu, setiap permintaan aplikasi harus masuk ke data organisasi yang tepat.

Cara saya menyelesaikannya

Saya memisahkan data pusat untuk organisasi dan akses dari data acara serta tamu milik tiap organisasi. Subdomain menentukan konteks penyelenggara, lalu basis data PostgreSQL tersendiri menyimpan data operasionalnya. Proses pembuatan organisasi juga menyiapkan basis data, migrasi, serta peran dan menu awal agar ruang kerja langsung dapat digunakan.

Laravel menangani proses penyiapan organisasi dan permintaan aplikasi; React dan Inertia menyajikan antarmukanya. Redis mendukung sesi, cache, dan pekerjaan antrean. Semua itu mengikuti keputusan yang sama: administrasi platform terpusat, pekerjaan tiap penyelenggara terpisah.

Hasil yang dibangun

Operator dapat mengelola organisasi tanpa mencampur data acaranya ke ruang administrasi bersama. Setiap penyelenggara bekerja dengan acara dan tamu miliknya melalui subdomain sendiri.

Ini proyek privat. Data klien, konfigurasi internal, dan kode sumber tidak dipublikasikan di sini. Diskusikan proyek serupa.
